### 🔧 阶段 2 修的问题

**⑯ "所有图片都显示有文字，而且显示的文字是文件名" → 修好了**

**这是我的一个字段用错了，两个现象同一个原因。**

我有个字段叫 `searchableText`（**搜索时**比对的文字），它**故意包含文件名**
（文件名有时有用，比如含日期的 `IMG_20240101`）。
但界面拿它来判断"这张图有没有文字"——**每张图都有文件名，所以永远为真**：

> 📌 **后续更正**：这个"文件名参与搜索"的想法**后来被用户否决了**
> （"没人会去记图片文件名"），阶段 3 已经把文件名从搜索里**彻底去掉**。
> 这里保留原文是为了说明当时的思路，**最终结论见 `docs/技术方案.md` §3.6.2**。

| 现象 | 原因 |
|---|---|
| 红点全部亮起 | 判断永远为真 |
| 大图页显示的"文字"是文件名 | 显示时把文件名也带出来了 |

**实际上识别是正常工作的**，数据库里存的是真文字，只是界面把它和文件名混在一起了。

**修法**：拆成两个属性——**判断和显示都不带文件名**。
搜索仍然带文件名（那是它的用途）。

> 📌 **教训**：一个"给搜索用"的字段被拿来"给界面判断用"，
> 而两者对"什么算内容"的要求不一样。**用途不同就该拆成不同的属性**，别图省事复用。

**⑰ 顺手加了个"识别自检"按钮**

相册页底部有个 **「识别不出来？点这里做个自检」**。
点了之后会对前 3 张照片跑完整识别流程，把真实数据显示出来，比如：

```
【第 1 张】IMG_20240101_120000.jpg
 记录尺寸: 4000×3000
 ① 缩小后尺寸: 1600×1200
 ② 识别原始结果长度: 37 个字
 ③ 洗过之后的文字: 某某超市 收银小票 ...
```

这样万一以后又认不出，一眼就能看出卡在哪一步，不用猜。

**⑱ "一张有文字的图都认不出来" → 读图片的方式不对（已修）**

**你发的自检结果一下子定位了问题**：三张图全部"**图片读取：失败（解码不出来）**"。

所以问题**不在识别器，而在读图片这一步**——我用 `BitmapFactory` 读相册的图片
**全部失败**，但 Coil 用同一个地址却能正常显示，说明是**读取方式**不合适。

**修法：三种读图方式逐个尝试，第一个成功的就用**

| 顺序 | 方式 | 说明 |
|---|---|---|
| 1 | 官方缩略图接口 | 安卓为"缩略图"设计的（安卓 10+），最省内存 |
| 2 | **新解码器** | 安卓 9+ 的新接口，对相册地址支持好 |
| 3 | 老解码器 | 最通用，兜底 |

**还顺手拦了一个隐患**：官方缩略图接口有时会给一张**很小**的图（比如 300×200），
那种尺寸**认不出小字**。所以加了门槛：**长边不到 700 就丢掉**，换下一种方式拿大图。

**自检现在会告诉你用的哪种方式**，例如：
```
① 读图成功（方式: ImageDecoder），尺寸: 1600×1200
```

> 📌 **教训**：读图片别只信一种 API。安卓有好几套图片读取接口，
> 对相册地址的支持不一样；而且"**能读到**"和"**读到的够清晰**"是两件事。

**⑲ 识别不准（认错、漏字、整张认不出）→ 提高识别分辨率**

**根因**：识别前我把图片缩到**长边 1600 像素**。你原图是 4000 像素级别，
这一缩**丢掉了 60% 的细节**，图里的小字（票据、截图、书页）就糊了。

**修法**：把识别用的最大边长从 **1600 提到 3000**，基本保留原始细节。
代价是慢一点（识别是一次性的，可以接受）。

> 🔧 **这是个"旋钮"**：嫌慢可以调小，嫌不准可以调大。

**⑳ 排查结果占满屏幕、看不到按钮 → 改成弹窗**

原因：排查结果做成了内嵌卡片，而里面的文字可以滚动——
在布局里这会**贪婪地吃掉全部高度**，把下面的按钮挤出屏幕。

修法：排查结果、出错提示、识别总结**全部改成弹窗**，
并且**限高 + 可滚动**（内容再多也不会把按钮挤出去），主界面完全不被占用。

**㉑ 新增「清空结果、重新识别全部」按钮**

因为**已经识别过的图不会再认一次**。你之前的识别是在旧的（低分辨率）设置下跑的，
所以必须能重跑。

> ⚠️ 这个按钮**只清机器认出来的文字，不会动你手动补的文字**。

**㉒ 顺带加了「识别完成」的提示弹窗**

跑完之后告诉你：一共识别多少张、多少张认出了文字、多少张没认出。

### 🚨 严重 BUG 修复

**㊵ 取消识别后点「继续」整个卡死 → 已修复**

**你描述的现象**：识别中点「取消」→ 再点「继续」→ **整个流程卡住**，
连切换相册都没反应，继续/取消按钮都失灵，进度条一直显示"已暂停"。

**根因：我用错了"是否正在跑"的判断依据。**

```kotlin
if (_ocr.value.isRunning) return // ❌ 致命错误
```

而 `isRunning` 的定义是 `已完成 < 总数`。**取消之后**（比如 5/100），
这个条件**永远为真** → 点「继续」被误判成"已经在跑了"，**直接忽略，什么都不做**。

于是死锁了：
1. 识别协程在"暂停循环"里**死等**一个永远不会来的继续信号
2. 「继续」按钮**永远清不掉**那个暂停标志
3. 那个悬挂的协程一直挂在总作用域上 → **把后续所有操作都拖住**（包括切相册）

**修法：用真实的任务句柄判断，而不是看进度数字。**

| 之前 | 现在 |
|---|---|
| 看 `done < total` 推断"在跑" | 看 **实际任务是否还活着**（`Job.isActive`） |
| 取消只是设个标志，等循环自己发现 | 取消**直接停掉任务**，立刻结束、不留悬挂 |
| "标记跳过"依赖循环收尾 | 单独跑一个任务去标记，**保证完成** |

> 📌 **教训**：判断"某个后台任务还在不在跑"，要问**任务本身**，
> 不能靠"进度数字看起来没走完"来推断。
> **进度是展示用的数据，不是控制状态** —— 拿展示数据当控制条件，
> 一旦遇到"取消 / 失败 / 中断"这些非正常路径，判断就会失真，然后卡死。

### 🐛 修：删不掉机器认的文字 + 滚轮抖动

**76. 机器认错的文字删不掉了 → 修好**

**你的反馈**：
> 有些没有文字的图片，机器扫描出来会有文字，我需要把识别出来的文字删掉，
> 但是删完又变成机器识别的文字了。

**这是我设计的语义漏洞。** 我原本定的是「框里为空 = 恢复机器识别」，
于是你**永远删不掉** —— 删空 → 保存 → 又变回机器文字。

**✅ 改成"三态"**：

| 状态 | 含义 | 实际显示 |
|---|---|---|
| 你**没动过** | 用机器识别的 | 机器文字 |
| 你**明确删空** | 这张图就是没字 | **空**（不再回退） |
| 你**写过内容** | 用你写的 | 你写的 |

**配套加了一个按钮**：弹窗里新增「**恢复机器识别结果**」
（**只有你改过之后才出现**），想反悔就点它。

另外，输入框清空时会提示「保存后这张图就当作没文字」，
免得你以为是"恢复机器文字"。

> 📌 **教训**：**"空值"和"没填"是两回事，数据库字段必须能区分。**
> 用 `null` 表示"没动过"，用 `""` 表示"明确清空"。
> 只要功能允许用户**覆盖系统默认值**，这个区分就**必须有** ——
> 否则用户根本没有手段表达"我就是要空"。

**77. 年份滚轮快速滑动会"鬼畜抖动" → 修好**

**你的反馈**：
> 在滚轮选择年份的时候，快速滑动会导致年份文字出现跳动鬼畜。

**根因是"双向绑定"形成的回环**：

```
居中项变化 → 通知父级 → 父级改选中值
 → 又触发 scrollToItem 滚回那个位置
 → 和正在进行的惯性滑动抢位置 → 抖
```

快速滑动时"居中项"**每帧都在变**，这个回环每秒触发几十次，
两个方向的滚动指令互相打架，画面就跳来跳去。

**✅ 现在改成三条**：

| 改动 | 效果 |
|---|---|
| **只在滚动停下后**才通知父级 | 不再每帧通知，不会打架 |
| **高亮跟着实时位置** | 拖动过程中依然跟手 |
| **只有年份列表变短时**才主动滚一下 | 平时绝不主动滚动 |

**顺带修了一个隐藏的计算错误**：原来判断"中间是哪一项"用的是
`离视口顶边最近的项`，那不是中间那项。现在按**视口中线**算，更准。

> 📌 **教训**：**"UI 控件 ↔ 外部状态"双向同步时，必须有一方是权威。**
> 滚轮位置该由**滚动本身**决定，外部状态只做初始值和越界修正。
> 一旦外部状态反过来每帧驱动滚动，就会和惯性动画打架。

### 🐛 修：换相册时识别没停，还在空跑

**75. 换相册立刻中止识别**

**你的反馈**：
> 在文字识别过程中切换相册，识别应该自动取消，而不是继续。

**这个 bug 的后果**：识别跑着的时候去扫别的相册，
识别**照旧继续跑** —— 进度条一直走、时间照样耗，
但那些照片记录马上就被删掉了，**纯属白跑一趟**。

**根因：取消的时机放错地方了**

我一开始想的是"监听到相册变了就取消"。
但**相册名是扫描结束后才变的**（要等新照片写进数据库）——
等它变才取消，**整个扫描期间识别都还在跑，根本来不及**。

**✅ 改成在"扫描开始时"就中止：**

```kotlin
private fun scanAlbumInternal(album: AlbumInfo) {
 abortOcrQuietly // ← 先中止识别，再开始扫描
 viewModelScope.launch { repository.scanAlbum(album) { ... } }
}
```

**⚠️ 这里有个坑我特意避开了**

现成的 `cancelOcr`（用户点"取消"用的）**不能直接拿来用** ——
它收尾时会把**剩下的照片标记成"跳过"**。在换相册场景下这会出问题：

| 情况 | 后果 |
|---|---|
| 给即将被删掉的旧照片标"跳过" | 没意义（马上就被删了） |
| **万一标记晚于新相册写入** | **把新相册的照片全标成"跳过"** → 界面莫名显示"还有 N 张未识别（上次取消了）" |

所以加了一条独立路径 **`abortOcrQuietly`**：
**只叫停、不标记、进度归零**。

> 📌 **教训**：**"同一个动作"在不同场景下，收尾方式可能完全不同。**
> - "用户主动点取消" → 要**留痕迹**（标记跳过，下次能接着来）
> - "因为客观原因被打断"（换相册）→ 该**干净地消失**，不留任何痕迹
>
> 把两者塞进同一个函数，**迟早会在角落里炸出来**。

### 🔧 理解阶段只做一次，跨批次复用

**74. 「继续搜下一批」不再重新理解**

**你的原话**：
> ai 搜索过一次后，继续搜索剩下的图时，ai 搜索的理解阶段应该不变，
> 不要搜索一次就重新理解一遍，这样会导致理解误差让搜索不准确。

**这个判断完全正确，原因很具体**：

理解阶段是把「无声铃鹿」翻译成一份**特征清单**。
**每次调用模型，措辞都会略有不同**：

| 第一次 | 第二次 |
|---|---|
| 浅**栗**色中长发、马耳、紫红眼睛 | 浅**棕**色中长发、马耳、紫红色眼睛 |

**判断标准就飘了** —— 第一批按"浅栗色"挑、第二批按"浅棕色"挑，
你就会觉得"同样的搜索怎么时好时坏"。

**而且白花钱**：理解阶段带着一次联网搜索（¥0.005/次），每批都重做就是重复付费。

**改好了**：

| 改动 | 效果 |
|---|---|
| 理解结果存下来 | 第一批算完就缓存 |
| 下一批直接复用 | **不再调接口**，用同一份特征清单 |
| 搜索时显示 | 「**沿用上次的理解结果，正在比对…**」 |

**缓存不会用错**（三个条件都满足才复用）：
```
① 你没关掉"理解"开关
② 描述没变
③ 上次确实算成功了
```

**什么时候清**：

| 情况 | 清吗 | 为什么 |
|---|---|---|
| **换相册** | ✅ 清 | 换了一整个照片库 |
| **改描述** | ✅ 自动失效 | 描述一变就自动重算，不用手动 |
| 改筛选条件 | ❌ 不清 | 条件不影响"这东西长什么样"，标准该一致 |
| 点「重新开始」 | ❌ 不清 | 按钮只写了"忘掉已比对记录" |

> 📌 **教训**：**调大模型时，"同一件事"要固定下来，不要反复问。**
> 模型对同一个问题会给出**措辞不同**的答案 ——
> **凡是"结论要给后续步骤当基准"的调用，都应该缓存复用**，
> 否则每一步的基准都在微小漂移，最后结果就不可复现。

### 🔧 阶段 3 调整（第五轮，

**51. 滚动位置：找到真正的原因了（我上一轮的结论是错的）**

**你实测**：去掉时间戳后，**打开大图退出还是回到顶端**。你判断得很准。

**真正的原因跟签名完全无关**，是 `LaunchedEffect` 的行为：

| 步骤 | 发生了什么 |
|---|---|
| 1 | 打开大图时，整个网格被跳过（`return`），**从界面上消失** |
| 2 | 关闭大图时，网格**重新挂载**（相当于第一次装上去） |
| 3 | `LaunchedEffect` 在**每次挂载时都会执行一遍** |
| 4 | 它执行的内容就是"回到顶部" → **所以每次都跳** |

**关键知识点**：
`LaunchedEffect(签名)` 里的"签名"只能决定**在同一次挂载期间**要不要**重启**它。
而网格每次重新出现都是**全新挂载**，所以它**必然跑一次** —— 跟签名变没变**无关**。

**所以正确做法是**：记住"上次用的是哪个签名"，**比较两次是否不同**：

```kotlin
if (lastSignature != scrollSignature) { // 只有真的不同才回顶部
 onSignatureApplied(scrollSignature)
 gridState.scrollToItem(0, 0)
}
```

"上次的签名"存在"大脑"里（比界面活得久），所以网格重新挂载时它还在 ——
一比较发现**没变**，就不回顶部了 ✅

**另外修了一个隐患**：搜索页和浏览页**各自用一份签名**。
原来共用一份的话，在搜索页改了条件会顺带把浏览页的签名也改掉，两个页面互相干扰。

### 🔧 根据你的试用反馈修的（第 7 轮，

**⑭ 拖动不跟手 → 终于找到真正原因：修饰符顺序放错了**

前六次我改了五遍**算法**（状态存储、增量计算、手写手势循环、图片解码尺寸），
**全都没用**。真正的原因是 **`pointerInput`（手势）和 `graphicsLayer`（缩放）的先后顺序**。

**原理**：Compose 的修饰符是**从左到右依次作用**的，所以手势收到的坐标
取决于它排在谁后面：

| 写法 | 结果 |
|---|---|
| `graphicsLayer` 在前、`pointerInput` 在后（❌ 之前的写法） | 手势在**放大后的坐标系**里 → 放大 3 倍时，手指移动 3 像素被读成 1 像素 → **图片只走 1/3** |
| `pointerInput` 在前、`graphicsLayer` 在后（✅ 现在） | 手势拿到**未缩放**的坐标 → **1:1 跟手** |

**这就是"手指划 3 厘米、图只走 1 厘米"的数学解释**——正好是 3 倍缩放。

**为什么这么难找**：这个 bug **只在放大后出现**（1 倍时除以 1，看不出问题），
所以特别容易被误判成"放大相关的算法问题"。而我一直没动过**顺序**这个维度。

> 📌 **教训**：一个 bug 改了三次还在原地，就要换**维度**去查——
> 不只是换算法，还要问"是不是位置/顺序/环境的问题"。

**⑬ 拖动不跟手 → 查了官方文档，找到真正原因（不是手势问题！）**

**前四次我都在改手势算法，全都没用——因为方向错了。**

真正的原因：**图片太大，GPU 每帧都要重新缩放整张原图。**

你的照片是 4000×3000 级别，之前 App 直接加载**原图**，
虽然显示时缩到了屏幕大小，但**每帧都要从原图重新采样**。
拖动时每秒几十帧都做这件事 → 又卡又慢，手感就是"不跟手"。

**解法（官方推荐）**：让图片在**解码阶段**就先缩到屏幕大小，而不是拿原图去缩放。

> ⚠️ 顺带差点踩一个坑：图片缩小后，"图片尺寸"就变成屏幕大小了，
> 而边界限制是靠它算的 —— 继续用会让**放大后反而拖不动**。
> 所以边界改用"照片本身的宽高比"来算（数据库里就有这个数据）。

**参考**：
- [优化位图图像 · Android 官方](https://developer.android.com/develop/ui/compose/graphics/images/optimization?hl=zh-cn)
- [graphicsLayer：Compose 里的防重组武器](https://www.dantech.academy/en/blog/android/graphicslayer-chong-recomposition-jetpack-compose)

**还顺手做了**：缩放上限从 8 倍降到 4 倍（倍数越大越吃性能）。

> 📌 **一个教训**：一个功能改了四遍都没好，就该**停下来查资料**，
> 而不是继续用同样的思路改代码。这次是查官方文档才找到真正原因的。

**② 时间显示规则（改了三次，最终拍板）→ 用「文件到本机的时间」**

**规则很简单**：不看照片什么时候拍的，只看**这个文件是什么时候出现在这台设备上的**。

你举的例子就是标准：别人 2024 年拍的照片，2025 年用社交软件发原图给你，
你保存到手机 —— 那就显示 **2025 年**。

现在取时间的顺序（首选 → 兜底）：

1. **文件自己的创建/修改时间** ← **（首选，就是"到本机的时刻"）**
2. 系统记录的加入相册时间
3. 图片 EXIF 里的拍摄时间（只兜底，绝不当主标准）

> 📌 **反过来说清楚**：你 2021 年拍的老照片，2025 年搬家过来，
> 现在会显示 **2025 年**（因为文件是 2025 年到这台手机的）。
> **这是你要的规则，不是 bug。**

> 「约」字表示这张图的时间不是从首选字段取到的（退而求其次），可以留意一下。

**③ 年份按钮里的数字换行了 → 已修**

现在放不下时会把**整个按钮**移到下一行，并且按钮里的文字强制不换行。
