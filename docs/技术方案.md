### 0.6 环境踩过的坑

| 现象 | 真正原因 | 解法 |
|---|---|---|
| `Could not create parent directory for lock file C:\...\.gradle\...` | 环境变量是"会话之外"设的，进程读到的是旧值 | 编译命令里**显式设** `GRADLE_USER_HOME` |
| `Configuring project with invalid directory` / `error = 5` | 沙箱不给编译进程写工作区权限 | 放开权限运行 |
| `Your project path contains non-ASCII characters` | `<工作目录>` 含中文 | 加 `android.overridePathCheck=true` |
| `Using kotlin.sourceSets DSL ... is not allowed with built-in Kotlin` | AGP 9 内置 Kotlin 与 KSP 冲突 | 加 `android.disallowKotlinSourceSets=false` |
| 一堆"找不到 emptyList / runCatching"的假错误 | Kotlin 编译器 2.2 读不懂 2.4 的基础库 | 把 Kotlin 升到 `2.4.10` 对齐 AGP |
| KSP 插件 `2.4.10-2.0.4` 找不到 | KSP 改版本号规则了 | 用 `2.3.12` |
| 安装包里混进 `INTERNET` 联网权限 | Coil/OkHttp 这些库自动带进来的 | 用 `tools:node="remove"` 从最终包里剔掉 |
| `Unresolved reference 'Icons'` | 图标不在 `material3` 里 | 加依赖 `material-icons-core` |
| `This material API is experimental` | `TopAppBar` 等是试验性 API | 给用了它们的 `@Composable` 加 `@OptIn(ExperimentalMaterial3Api::class)` |
| `ServiceCompat.startForeground` 找不到 | 该版本没有这个便捷方法 | 直接用 `Service.startForeground(id, n, FOREGROUND_SERVICE_TYPE_DATA_SYNC)`（**这是做后台识别时的历史问题，那部分代码已删除**） |
| `filterQuality` 不是 `graphicsLayer` 的参数 | 这个 Compose 版本里没有 | 删掉不用 |
| `Size` / `size(...)` 解析不了 | Coil 3 的 `Size` 在 `coil3.size` | 用 `builder.size(w, h)`（Int 重载） |

## 1. 当前架构（已实现）

### 1.1 四个页面

用**一个 `Screen` 枚举**管理"现在在哪一页"（**不用**引导航库）：

```kotlin
enum class Screen { ALBUM, ANALYZE, PHOTOS, SEARCH, AI, SETTINGS }
```

| 页面 | 枚举 | 内容 |
|---|---|---|
| **① 选择相册** | `ALBUM` | App 启动页。**顶部只有应用名，中间整块给相册列表，底部一个扫描按钮** |
| **② 识别分析** | `ANALYZE` | 扫描完成后**自动跳转**。识别进度 + 统计 + 操作按钮；**最底部是「按图片内容搜索」入口** |
| **③ 浏览图片** | `PHOTOS` | 照片网格 + 筛选条（**文件格式** / 年份范围 / 文字） |
| **④ 搜索图片** | `SEARCH` | 搜索框 + 同一套筛选条 + 结果网格 |
| **⑤ 按图片内容搜索** | `AI` | 描述 + 强制先设条件 + AI 结果（**会联网**） |
| **⑥ 设置** | `SETTINGS` | 填 AI 密钥、选服务商、测试连接 |

**返回逻辑**：`goBack` 统一处理 —— `SEARCH/PHOTOS → ANALYZE → ALBUM`。
每个页面左上角都有 **←** 按钮，**手机返回键也走同一条逻辑**（`BackHandler`）。

> **为什么用枚举而不是多个布尔值**：布尔值会出现"两个页面同时为 true"这种矛盾状态，
> 而且"返回上一页"要写一堆判断。枚举让状态只有一种可能，返回逻辑一目了然。

### 1.3 界面状态放在哪（重要约定）

| 状态 | 放哪 | 为什么 |
|---|---|---|
| 当前页面 | `PhotoViewModel.screen` | 要跨屏幕存活 |
| **网格滚动位置** | `PhotoViewModel`（`browseGridState` / `searchGridState`） | 打开大图时网格会被销毁重建，放界面里会丢 |
| **"上次滚动到顶部用的条件签名"** | `PhotoViewModel`（`searchScrollKey` / `browseScrollKey`） | 同上，而且要比界面活得久 |
| 弹窗开关（`showTierDialog` 等） | 界面里 `remember` | 不需要跨屏幕 |
| 诊断/完成/出错弹窗 | **最外层 `MainScreen`** | 全局提示，写在页面里会出现"点了没反应" |

## 2. 数据层

### 2.1 数据库版本历史（现在 **version = 5**）

| 版本 | 改了什么 | 副作用 |
|---|---|---|
| 1 | 最初，时间是"加入相册时间" | — |
| 2 | 改成"图片自带的拍摄时间"（EXIF） | 需要重扫 |
| 3 | 改成"**文件到本机的时间**"（`DATE_MODIFIED`） | 需要重扫 |
| 4 | 新增 `ocr_cache` 表（识别结果长期缓存） | **需要重扫 + 重新识别** |
| **5** | `ocr_cache` 增加 `bucket_name`（可按相册统计） | **需要重扫 + 重新识别** |

> ⚠️ **`fallbackToDestructiveMigration`**：版本对不上就**清空重建**。
> 所以**每次升版本，用户都要重新扫相册**。
> **阶段 5 接入 AI 时不要再动表结构** —— `ai_description` / `ai_state` 两个字段**已经预留好了**。

### 2.2 照片表 `photos`

| 字段 | 说明 |
|---|---|
| `id` / `uri` / `name` / `bucket_name` | 基本信息 |
| `width` / `height` / `size_bytes` / `date_millis` / `date_source` | 文件信息 |
| `ocr_text` / `ocr_state` | **文字识别**结果 |
| `user_text` | **用户手动补的文字**（阶段 4 用，已预留） |
| `ai_description` / `ai_state` | **用不上了**（见下方说明） |

> **关于 `ai_description` / `ai_state`**：
> 这两个字段是当初"**预先全扫整个相册、把 AI 的描述存下来**"那个方案预留的。
> 后来用户否决了那个方案（理由：识别结果没法保存、不现实），
> 改成"**搜索时只把候选图发给 AI 比对**" —— 这个方案**不需要存任何东西**。
>
> **所以这两个字段现在是空的、不会写入**。
> 保留它们是为了**避免升数据库版本**（升版本会让用户重扫相册）。
> 将来如果真要做"图片内容描述"这类功能，可以复用。
> `PhotoDao.updateAiDescription` 也保留着（目前无人调用）。

**三个"取文字"的属性，一定要分清**：

| 属性 | 含文件名？ | 用在哪 |
|---|---|---|
| `searchableText` | 含 | 只给别处方便用 |
| `hasRecognizedText` | **不含** | 判断"这张图有没有文字"（红点、筛选） |
| `recognizedText` | **不含** | 界面上显示 |

> ⚠️ 之前用 `searchableText` 判断"有没有文字"，结果**每张图都有文件名 → 全都被认为有文字**。
> 这个坑已修，**以后判断有没有文字必须用 `hasRecognizedText`**。

**日期取值顺序**（`DATE_MODIFIED` → `DATE_ADDED` → `DATE_TAKEN`）：

| 优先级 | 取自 | 含义 |
|---|---|---|
| **1（首选）** | `DATE_MODIFIED` | **文件自己的修改时间 = 文件到本机的时刻** |
| 2 | `DATE_ADDED` | 系统记录的"加入相册时间" |
| 3 | `DATE_TAKEN` | EXIF 拍摄时间（**只兜底，绝不当主标准**） |

**用户拍板的规则**（改过三次，**别再改**）：
> 不看照片什么时候拍的，只看**这个文件在这台设备上是什么时候创建的**。

**用户举的例子**：别人 2024 年拍的照片，2025 年用社交软件把**原图**发给我，
我保存到手机 —— 这张图就显示 **2025 年**。

> **注意副作用**：换手机搬家过来的 2021 年老照片会显示成**搬家的年份**。
> **这是用户明确要的规则，不是 bug。**
> 界面上 `date_source != FILE_MODIFIED` 时加「约」字，帮用户看出"时间退而求其次取到的"。

### 2.3 识别缓存表 `ocr_cache` ★

**为什么单独存一份**：用户要求"目录里一次只装一个相册"，
所以**换相册时旧相册的记录会被删掉**。如果识别结果只存在照片记录上，
换回旧相册就得**重新识别一遍** —— 而识别是最费时间的操作，白做太浪费。

```kotlin
@Entity(tableName = "ocr_cache")
data class OcrCacheEntity(
 @PrimaryKey val uri: String, // 图片地址（稳定，换相册也是同一个）
 val ocrText: String?,
 val ocrState: Int,
 val bucketName: String = "", // 记相册名，可按相册统计
 val cachedAt: Long,
)
```

**两处关键接线**：

1. **扫描相册之后** → `restoreOcrFromCache(uris)`，把缓存填回照片记录：
 ```sql
 UPDATE photos SET ocr_text = :text, ocr_state = :state
 WHERE uri = :uri AND ocr_state = 0 -- 只填从没识别过的，不覆盖
 ```
2. **识别完成时** → 把结果 `put` 进缓存

**效果**：识别过的图，**换回任何相册都不用再认**；只认"从没见过"的图。

**按相册统计**（「已识别相册」弹窗用）：

```sql
SELECT bucket_name AS bucketName,
 SUM(CASE WHEN ocr_state = 1 THEN 1 ELSE 0 END) AS recognized,
 SUM(CASE WHEN ocr_state = 2 THEN 1 ELSE 0 END) AS noText
FROM ocr_cache
WHERE bucket_name != ''
GROUP BY bucket_name
ORDER BY COUNT(*) DESC
```

> 注意：`ocr_state = 3`（用户取消时跳过的）**不算识别结果**，统计里排除。

## 3. 功能实现与踩过的坑

### 3.1 相册权限（**曾经最大的坑**）

**症状**：App 装好后显示"没找到任何相册"，但手机里明明有几千张图。

**根因**：清单里声明 `READ_MEDIA_IMAGES` **只算"报名"，不算"获批"**。
安卓 6.0 以后危险权限必须在**运行时弹窗申请**。
之前漏了这一步，`contentResolver.query` 拿不到任何数据 → 列表为空。

**⚠️ 一个极其容易搞错的细节**：

安卓 14+ 有 `READ_MEDIA_VISUAL_USER_SELECTED`（"只允许部分照片"）：
- **清单里要声明**（否则部分授权会出问题）
- **申请列表里绝对不能带上它！**

如果申请列表写成 `[READ_MEDIA_IMAGES, READ_MEDIA_VISUAL_USER_SELECTED]`，
系统就只弹"仅选择照片"的窗口，用户选完还是只能看到勾的那几张，
**不会**出现"允许全部 / 仅选择照片"的选择界面。

正确写法：安卓 13+ **只申请 `READ_MEDIA_IMAGES`**，系统自己会给出完整的三选项弹窗。

**另外**：用户主动选"部分照片"是合法状态，要当"能用"处理，同时界面提醒。

### 3.2 相册列表适配不同手机

安卓有个 **MediaStore 总索引表**，不管照片躺在 `DCIM`、`Pictures`、`Download`，
系统相册程序扫到后都会登记进去。所以我们的做法是**问系统"你有哪些相册"**，
而不是自己翻文件夹路径 —— 各品牌手机都能适配。

代码里做了三层兜底：
1. 主要用 `BUCKET_DISPLAY_NAME`
2. 拿不到就用 `RELATIVE_PATH`
3. 万一 `BUCKET_ID` 是空的，用路径或名字当编号

**已知局限**：照片放在系统扫描不到的隐藏目录里，MediaStore 里就没记录，我们也看不到。

### 3.3 诊断工具

界面上有 **「诊断」** 按钮（`MediaStoreReader.diagnose`），
把系统实际交出的数据原样报告：一共多少张图、按目录分别多少、有没有查询报错。

**⚠️ 弹窗位置**：诊断结果 / 识别完成 / 出错，这三个弹窗都在**最外层 `MainScreen`**。
曾经写在相册页里，导致**在搜索页点诊断没反应**（数据算出来了，但当前页面没地方弹）。

### 3.4 全屏看大图

**现在有的功能**：
- 双指捏合缩放（1×～4×）
- 放大后单指拖动看细节（带边界限制）
- 双击放大 / 复位
- 单击隐藏/显示文件信息和手机状态栏（沉浸式）
- 点左上角关闭，按返回键也能关

**⚠️ 用户明确要求删掉的**：**左右滑动切换上一张/下一张**。
所以**没有** `HorizontalPager`，也没有"哪一页被放大"的判断逻辑。**别再把它加回来。**

#### 3.4.1 ⚠️ 手势最大的坑：`pointerInput` 必须在 `graphicsLayer` **之前**

**症状**：放大之后拖动图片，**手指划 3 厘米、图只走 1 厘米**。
**这个 bug 改了 5 轮**，前 4 轮都在改手势算法（全部无效）。

**真正的根因**：**修饰符顺序**。
`pointerInput` 写在 `graphicsLayer` **后面**时，手势拿到的坐标是**被缩放系数除过的**。

```kotlin
// ❌ 错：手势坐标被缩放系数除过，所以拖得慢
Modifier
 .graphicsLayer { scaleX = scale; scaleY = scale }
 .pointerInput(Unit) { ... }

// ✅ 对：手势先拿到原始坐标
Modifier
 .pointerInput(Unit) { ... }
 .graphicsLayer { scaleX = scale; scaleY = scale }
```

> **教训**：Compose 的**修饰符顺序决定行为**，`pointerInput` 尤其敏感。
> 手势"变慢 / 变快 / 偏移"这类症状，**先检查修饰符顺序**，别急着改算法。

#### 3.4.2 单击 + 双击必须共用一个检测器

```kotlin
// ✅ 对
detectTapGestures(onTap = { ... }, onDoubleTap = { ... })

// ❌ 错：第一个检测器会消费掉事件，双击永远收不到
detectTapGestures(onTap = { ... })
detectTapGestures(onDoubleTap = { ... })
```

**副作用**：单击有约 0.3 秒延迟（系统要等一会儿确认不是双击）。**这是安卓标准行为，正常。**

#### 3.4.3 每帧都变的量不要用 `Animatable`

拖动是**每帧**都在变的值。用 `Animatable.snapTo` 会**每帧取消并重建协程**，开销很大。
**直接用普通的 `mutableStateOf`**。

#### 3.4.4 长图要用 `size` 指定解码尺寸

长图如果按原始尺寸解码，GPU 每帧都要重采样整张位图，很卡。
用 Coil 的 `ImageRequest.Builder.size(w, h)` 让图片**在解码阶段就缩到显示大小**。

> ⚠️ 同时**边界限制必须改用"照片宽高比"计算** ——
> 因为边界是靠图片尺寸算的，改了显示尺寸会让边界失效（"改了 A 带坏 B"的实例）。

### 3.5 识别文字 ★

**方案**：ML Kit 中文文字识别，**完全在手机本地跑，不联网、不上传、不收费**。

| 参数 | 值 | 说明 |
|---|---|---|
| `MAX_OCR_SIDE` | `3000` | 识别前把图缩到这个边长（太小会认不准，太大耗内存） |
| `MIN_TEXT_LENGTH` | `2` | 少于 2 个字不算 |
| `MIN_USABLE_SIDE` | `1400` | 低于这个尺寸就换一种解码策略 |

#### 3.5.1 图片解码要三层兜底

**症状**：识别一张都认不出来，自检显示"图片读取：失败（解码不出来）"。

**根因**：`BitmapFactory.decodeStream` 在 `content://` 这种地址上会失败。

**解法**：三层策略，依次尝试
1. `loadThumbnail`（带尺寸门槛）
2. `ImageDecoder`
3. `BitmapFactory`

#### 3.5.2 识别要跑在**专用线程**

文字识别是重计算。跑在主线程会卡界面；跑在普通线程池里，
切后台时会被系统冻结（**症状：进度跑一小段就停住，回前台又继续**）。

**解法**：`Executors.newSingleThreadExecutor` 做成**专用单线程**，
整条链路（读图片 → 识别 → 回调）都在上面跑，**完全不碰主线程**。

#### 3.5.3 取消/继续：判断"在不在跑"必须用 `Job`，**不能看进度数字**

**这是一个严重 bug，值得完整记录。**

**症状**：识别中点「取消」→ 再点「继续」→ **整个流程卡死**，
连切换相册都没反应，继续/取消按钮都失灵。

**根因**：

```kotlin
if (_ocr.value.isRunning) return // ❌ 致命
```

而 `isRunning` 的定义是 `已完成 < 总数`。
**取消之后**（比如 5/100）这个条件**永远为真** →
点「继续」被误判成"已经在跑了"，**直接忽略，什么都不做**。

于是死锁：
1. 协程在"暂停循环"里**死等**一个永远不会来的继续信号
2. 「继续」按钮**永远清不掉**那个暂停标志
3. 悬挂的协程挂在 `viewModelScope` 上 → **把后续所有操作都拖住**（包括切相册）

**正确做法**：

```kotlin
private var ocrJob: Job? = null

fun startOcr {
 if (ocrJob?.isActive == true) return // ✅ 问任务本身
 ocrJob = viewModelScope.launch { ... }
}

fun cancelOcr {
 repository.cancelOcr
 ocrJob?.cancel // ✅ 真的停掉，不留悬挂
 ocrJob = null
 _ocr.value = PhotoRepository.OcrProgress // 界面回到"没在跑"
 viewModelScope.launch { repository.skipRemainingOcr } // 单独标记跳过
}
```

**两个配套要点**：
1. **"标记跳过"不能依赖识别循环自己收尾** —— 我们是强行 cancel 的，
 循环里的清理代码不一定会执行到。所以要**单独跑一个协程**去标记。
2. 协程里要正确区分"取消"和"真出错"：
 ```kotlin
 catch (e: CancellationException) { throw e } // 取消是正常流程
 catch (e: Exception) { ... } // 这才是错误
 ```

> 📌 **教训**：判断"某个后台任务还在不在跑"，要问**任务本身**（`Job.isActive`），
> 不能靠"进度数字看起来没走完"来推断。
> **进度是展示用的数据，不是控制状态。**

#### 3.5.4 为什么**不做**后台识别

**用户实测**：切到别的 App 后识别会停住。

**试过四种方案，全都不行**：
协程 → 前台服务 → 独立线程 → 唤醒锁 + 电池白名单。

**根因（有权威依据）**：
[OEM Compatibility Guide](https://github.com/Ikolvi/Tracelet/blob/main/help/OEM-COMPATIBILITY.md) 明确写着：

> 华为、小米、一加、三星、OPPO、**vivo** 等厂商都自带一套省电管理，
> 会主动杀掉后台应用 —— **即使是配置正确的前台服务 + START_STICKY + 唤醒锁也一样**。

vivo 被评 **3/5 级**，机制是"**后台活动管理器**"。

**用户最终决定**（很实际）：
> 用户想继续用手机可以把 App 切成**小窗**，这样识别正常进行，同时也能用手机。

**所以做了大扫除**，删掉了为后台而加的全部东西：

| 删掉的 | 原因 |
|---|---|
| `OcrService.kt`（整个前台服务） | 不再需要 |
| `FOREGROUND_SERVICE` / `FOREGROUND_SERVICE_DATA_SYNC` | 同上 |
| `POST_NOTIFICATIONS` + 通知弹窗 | 没有通知了 |
| `WAKE_LOCK` + 唤醒锁代码 | 前台时 CPU 本来就不会睡 |
| `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` + 入口 | 同上 |

**现在的权限只剩 4 条**（安装包里实测确认）：
```
READ_MEDIA_IMAGES / READ_MEDIA_VISUAL_USER_SELECTED / READ_EXTERNAL_STORAGE(max 32)
ACCESS_NETWORK_STATE ← ML Kit 库自带的，App 仍然【没有】联网权限
```

> **教训**：**要尊重平台现实。**
> 花在"对抗系统限制"上的时间，不如用来把核心功能做好。
> 而且这是**用户自己提出的更优解**（小窗），比程序员硬啃系统限制高明。

### 3.6 搜索 ★

> **这一节在 改过一次**：原来用的是"打分排序"（完整匹配 100 分、部分匹配 40 分…），
> **现在改成了"按空格分词 + 不排序"**（用户要求）。
> 打分那套（`SearchScorer` / `SearchHit`）**已经删掉了**，现在的实现是 `data/TextMatcher.kt`。

#### 3.6.1 ★ 分词规则（用户 2026-10 明确要求）

**按空格把输入切开**，每一段是一个"词"，**所有词都要在图里找到**（顺序、位置都不限）。

| 输入 | 切出来的词 | 命中条件 |
|---|---|---|
| `ABC` | `["ABC"]` | 图里文字要含 `ABC`（**连着出现**） |
| `AB C` | `["AB", "C"]` | 要同时含 `AB` **和** `C` |
| `A B C` | `["A", "B", "C"]` | 要同时含 `A`、`B`、`C` 三个字 |

**用户原话**：
> 分词之后搜索不需要排序，只要图片内文字有匹配到的单字，就算搜索到。
> 词语中用空格分开后，就按空格前后的分词进行搜索。

**实现要点**（`data/TextMatcher.kt`，只有 87 行）：

```kotlin
// 1. 按空格切词（全角空格、制表符、换行、中英文逗号都当分隔符）
fun splitTerms(input: String): List<String> =
 input.split(' ', '　', '\t', '\n', '\r', ',', '，')
 .map { normalize(it) }
 .filter { it.isNotEmpty }

// 2. 每个词都要能找到（顺序不限）
terms.all { haystack.contains(it) }

// 3. 标准化：去掉所有空白 + 转小写
fun normalize(raw: String) = raw.filterNot { it.isWhitespace }.lowercase
```

**几个附带行为**：
- **空输入** → 返回全部（调用方一般是"只用条件筛选"）
- **结果按时间倒序**（新的在前）—— 不打分，所以用时间排
- **转小写** → 英文大小写不敏感（`hello` 能匹配 `Hello`）
- **去空白** → 图里识别出的文字如果带奇怪换行/空格，也能匹配上

> ⚠️ **注意一个容易搞混的点**：切词之后，**每个词内部还是"连着匹配"**。
> 所以输入 `ABC` 要求图里有连着的 `ABC`，**不会**退化成"有 A 和 B 和 C 就行"。
> 想变成单字匹配，就要**打空格**写成 `A B C`。这是用户明确要的行为。

#### 3.6.2 ⚠️ 搜索**不匹配文件名**（用户要求）

**用户原话**：
> 没有人会去记手机相册里的图片文件名。

**完全对。** `IMG_20240101_120000` 这种名字参与匹配只会带来无意义的命中。
所以 `TextMatcher` **只比对 `userText` 和 `ocrText`**。

#### 3.6.3 ★ 搜索可以叠加"确定的条件"（用户的核心设计）

**用户原话**（这段话是这一版搜索设计的核心，完整保留）：

> 我解释一下为什么要加条件，因为图片的文字识别中有很多识别错误的文字和字母，
> 这些会干扰搜索并将用户需要的图片往下面挤，所以需要添加用户已知的**必定条件**
> ——跟文字识别这种带有一定随机性的条件不一样——来进行筛选，
> 将**所有干扰项直接排除**，使搜索更精确。

**实现**：搜索流程分两步

```
第一步：用"确定的条件"先筛（文件格式 / 年份范围 / 有没有文字）← 排除干扰
第二步：在剩下的里面做分词匹配（每个词都要有）
```

**而且条件可以单独用**：不打字、只设条件 = 纯筛选。

> 📌 **这个设计思想很值得记住**：
> 当有一个**不可靠的信号**（OCR 有随机误差）时，
> 用**可靠的信号**（尺寸、时间）先把范围缩小，能极大提升结果质量。

#### 3.6.4 只搜当前相册

数据源是本地目录，而目录按用户要求**只装一个相册**的东西，
所以**天然就是"只搜这一个相册"**。顶栏会显示当前是哪个相册。

### 3.7 界面布局演进的最终形态

**走过的弯路**：最初把"选相册 / 扫描 / 识别"三步塞在一个页面里，
中间的相册列表被压得只剩很矮一条，没法滑。

**最终形态**：拆成四个独立页面（见 §1.1），
**删掉了所有"第 X 步"标题**。

**识别分析页的按钮位置**（用户要求）：

| 位置 | 内容 |
|---|---|
| 进度条/状态文字**正下方** | 暂停/取消/继续、「重新识别」「诊断」、**「按文字识别」** |
| 页面底部 | 「搜索图片」「浏览图片」 |
| **最后一行** | **「按图片内容搜索」**（标准按钮形状、文字居中、加粗蓝色） |

### 3.8 筛选条与滚动位置

#### 3.8.1 筛选条必须是一排

**症状**：年份按钮里的 "2023" 显示成两行。

**两层解法一起用才有效**：
1. **按钮里的文字**：`Text(maxLines = 1, softWrap = false)` —— 强制不换行
2. **容器**：现在用 `Row` + 三个按钮各 `weight(1f)` —— **平分宽度**，
 屏幕窄就自动变窄，**不换行**（用户明确说换行"很丑"）

文字也缩短以保证窄屏放得下：`有文字` → **`有字`**，`未识别到文字` → **`无字`**。

#### 3.8.1.1 ★ 年份筛选是**范围**，不是单个年份（用户 2026-10 要求）

**用户原话**：
> 将年份分类改成范围而不是单个年份，弹窗左边是起始年份，右边是结束年份，
> 比如左边通过滚轮选择了 2024 年，右边可选的年份就有 24、25、26 年，
> 然后搜索就按这个年份范围分类搜索。

**实现**（`YearRangePickerDialog` + `YearWheel` 两个组件）：

| 部分 | 说明 |
|---|---|
| **左滚轮** | 起始年份，列出**全部**有照片的年份（从老到新，上面老下面新） |
| **右滚轮** | 结束年份，**只列出起始年及之后的年份**（`asc.drop(startIndex)`） |
| **自动纠正** | 起始年往后挪导致结束年"越界"时，自动把结束年拉到最后一个可选项 |
| **确定** | 返回 `IntRange`（闭区间，含首尾） |
| **不限** | 返回 `null` |

**状态**：ViewModel 里从 `Int?`（单年）改成 **`IntRange?`**：
```kotlin
private val _filterYearRange = MutableStateFlow<IntRange?>(null)

fun setFilterYearRange(range: IntRange?) {
 _filterYearRange.value = range?.let {
 if (it.first <= it.last) it else it.first..it.first // 防御：别出现"负数区间"
 }
}
```

**筛选**：`yearOf(photo.dateMillis) in yearRange`。

**按钮上的文字**：同一个年份显示 `2024`；跨年显示 **`2024-2026`**；
范围文字较长时字号自动缩到 11sp，保证**三个按钮还是排成一排**。

> **为什么这个改动值得记**：它体现了"**范围条件**"和"**单值条件**"在实现上的差别 ——
> 单值只要 `==`，范围要 `in`，而且 UI 要**两个滚轮联动**（右滚轮的选项依赖左滚轮的值）。
> 联动时一定要处理"**原来的选择变得不合法**"这种情况（这里是自动纠正结束年）。

#### 3.8.1.2 ★ 筛选条件从「清晰度」换成「文件格式」（用户 2026-10 要求）

**用户原话**：
> 把清晰度条件改掉，改成文件格式分类，一种是 GIF，一种是图片格式，
> 以后不需要清晰度分类，搜索页和浏览页都要改。

**新枚举**（`model/SearchModels.kt`）：

```kotlin
enum class FileKind(val label: String) {
 GIF("GIF"), // 会动的图
 IMAGE("图片"), // JPG / PNG / WebP / BMP 等静态图

 companion object {
 fun fromName(name: String): FileKind =
 if (name.substringAfterLast('.', "").equals("gif", ignoreCase = true)) GIF else IMAGE
 }
}
```

`PhotoEntity.fileKind` 按**扩展名**判断（相册里的文件名都是系统给的，扩展名可靠）。

**⚠️ `ResolutionTier` 没有删掉**：
它现在**只用来"显示"**（缩略图和文件信息里标一下清晰度），
**不再是筛选条件**。文档里特意注明，避免以后有人看到它还在、又把它接回筛选里。

**清掉的死代码**：
- `PhotoRepository.tierBounds` —— 没人用了
- `FilterBar` 的 `onTierClick` 参数 → 改成 `onKindClick`

**顺带的显示改进**：大图的文件信息里，如果是 GIF 会**多标一个「GIF」**
（会动的图值得让人一眼知道）。

#### 3.8.2 ★ 滚动位置：这次修了**四次**，过程很值得记

**用户要求**：

| 场景 | 期望 |
|---|---|
| 打开大图 → 退出 | 位置**保持不变** |
| 改搜索词 / 筛选条件 | **回到顶部** |

| 第几次 | 做法 | 结果 |
|---|---|---|
| 1 | 只把浏览页的滚动位置存进 ViewModel | 搜索页漏了 → 还是跳 ❌ |
| 2 | 两页共用组件，签名里加"打开大图的时间戳" | 两页都跳 ❌ |
| 3 | 去掉时间戳（只留条件） | **还是跳** ❌ |
| 4 | **比较"两次签名是否不同"** | ✅ |

**真正的根因：`LaunchedEffect` 每次重新挂载都会执行**

```kotlin
// ❌ 错：每次网格重新出现都会滚回顶部
LaunchedEffect(scrollSignature) {
 gridState.scrollToItem(0, 0)
}
```

因为**打开大图时网格会被 `return` 跳过、从界面上消失**，
关闭大图时它**重新挂载** —— 而 `LaunchedEffect` **在每次挂载时都会执行一遍**。

> **关键知识点**：`LaunchedEffect(key)` 里的 key 只能决定
> **"在同一次挂载期间，key 变化时要不要重启这个 effect"**。
> 它**管不了"重新挂载"** —— 重新挂载时它一定会执行。
>
> 所以：**"只做一次"或"只在某个状态真的变化时才做"的逻辑，
> 不能直接写在 `LaunchedEffect` 里，必须自己比较"上一次的值"。**

**✅ 最终方案**：

```kotlin
// ViewModel 里各存一份"上次用的签名"（比界面活得久）
private val _searchScrollKey = MutableStateFlow("")
private val _browseScrollKey = MutableStateFlow("")

// 网格里比较（两个页面各用一份，不能共用！）
LaunchedEffect(scrollSignature) {
 if (lastSignature != scrollSignature) {
 onSignatureApplied(scrollSignature)
 gridState.scrollToItem(0, 0)
 }
}
```

**滚动状态放 ViewModel**（`browseGridState` / `searchGridState`）：
打开大图时网格会被销毁重建，`rememberLazyGridState` 记的位置会丢。

**两个页面各用一份签名**：共用一份的话，在搜索页改条件会顺带改掉浏览页的签名，互相干扰。

## 4. 核心教训（最重要的一节）

> 这一节是**用真实 bug 换来的**，比任何技术细节都值钱。

### 4.1 一个 bug 改了几次还不好，就停下来查资料

"拖动不跟手"**改了 5 轮**，前 4 轮都在改手势算法（全部无效）。
第 5 轮查官方文档才发现真正原因是**修饰符顺序**。

> **同样的思路改第三次还不行，说明你的前提假设错了，不是参数没调对。**

### 4.2 解释不了"为什么发生"，改的就是在碰运气

**滚动位置这个 bug 我错了两次**：

| 轮次 | 我的判断 | 结果 |
|---|---|---|
| 上一轮 | "看大图会导致界面重建，所以要加时间戳区分" | ❌ 反而每次看大图都跳 |
| 用户说我错后 | 我**立刻认同**"加时间戳自相矛盾"并去掉 | ❌ **还是错** |
| 这一轮 | 真正原因：`LaunchedEffect` 每次重新挂载都执行 | ✅ |

> **最重要的教训**：用户指出我错时，我**认同得太快了** ——
> 只凭"这个推理听起来有道理"就改了，**没有去验证"那原来的问题到底是怎么产生的"**。
>
> **一个 bug，如果你解释不了它为什么发生，那你改的东西就是在碰运气。**
> 正确顺序是：**先把"为什么"解释清楚，再动手改。**
>
> **而且**：用户的判断可能是对的，但**"用户说的原因"不一定是"真正的原因"**。
> 这次用户指出"不该加时间戳"是对的（加它确实有害），
> 但去掉它**并不能解决问题**。
> **纠正一个错误做法 ≠ 找到根因。**

### 4.3 不要把"不该触发重置的信号"放进触发重置的判据里

我加"打开大图的时间戳"是怕"关闭大图被误判成条件变了"，
但**条件确实没变，签名自然也不会变** —— 这个担心本身是多余的，**加变量反而制造了 bug**。

> **加的每一个变量都是一个新的出错点。**
> 遇到"看起来需要额外区分"的情况，**先确认判断依据本身够不够**。

### 4.4 用"展示数据"当控制条件是危险的

`isRunning` 是给界面显示进度用的，我却拿它判断"任务在不在跑"。
一遇到"取消"这种非正常路径，判断就失真，然后卡死。

> **判断任务状态要问任务本身**（`Job.isActive`），
> **进度是展示数据，不是状态机的状态。**

### 4.5 "取消"要真的把任务停掉

只设一个标志等循环自己发现 —— 依赖"循环能跑到检查点"，
一旦检查点没跑到（或标志被别的逻辑重置），就变成**永久悬挂**。
而且**清理逻辑不能依赖被 cancel 的协程自己去执行**。

### 4.6 全局性的提示不要写在某个页面里

诊断结果、错误、完成通知这类东西，用户可能在**任意页面**触发。
写在页面里就会出现"数据有了但没地方显示"。
**放在最外层，一次写好，处处都能弹。**

### 4.7 跨界面重建要保留的状态，放 ViewModel

滚动位置这类要跨"界面销毁重建"存活的状态，
放在界面里（`remember`）迟早会遇到"界面被重建 → 状态丢了"。

### 4.8 修 bug 时要主动检查"还有哪些地方是同一个模式"

滚动位置这个 bug，我第一次只改了用户报的那个页面，
**没想到另一个页面有同样的毛病**（因为是同一个我写的、同样的错法）。
**很可能不止一处。**

### 4.9 改了 A 要检查会不会带坏 B

"把图片缩小"差点让"拖动边界限制"失效 —— 因为边界是靠图片尺寸算的。

### 4.10 新引入一个状态值时，要回头检查所有统计/查询

加了"跳过"状态（`ocr_state = 3`）却忘了更新"待处理"的定义，
导致取消后"待识别数量"变成 0，界面以为全部完成。

### 4.11 拿不准的库接口，去查字节码或官方文档，不要猜

```powershell
# 解开 Gradle 缓存里的 aar → 取出 classes.jar → 解压
<JDK 目录>\bin\javap.exe -classpath <目录> <类名>
```

### 4.12 涉及"调用付费外部服务"的功能，优先"按需局部调用"

不要"全量预处理"。详见 §5.1。

#### 5.1.2 API 调用细节（**已核对官方文档**）

依据：[DeepSeek 图像理解官方文档](https://api-docs.deepseek.com/zh-cn/guides/vision/)

| 项目 | 做法 | 依据 |
|---|---|---|
| 模型 | `deepseek-flash` | 文档确认这是支持图片输入的模型 |
| 地址 | `POST {baseUrl}/v1/chat/completions` | OpenAI 兼容端点 |
| 传图方式 | `data:image/jpeg;base64,...` 内联 | 文档第 1 种方式（本地文件最简单） |
| 细节级别 | `detail: "low"` | 文档：缩到 512×512，更快更省 token |
| 图片位置 | **只放在 `user` 消息里** | ⚠️ 文档：放 `system`/`assistant` 会返回 **400** |
| token 消耗 | 每张图**最多 1024**（不论原图多大） | 文档确认 2000×2000 和 5000×5000 消耗一样 |
| 我们要缩到 | **长边 1024** | 官方会自动缩到约 1300×1300，1024 完全够 |
| 请求体上限 | 48 MiB | 我们额外做了 30 MB 的保险闸 |

**让 AI 只返回编号**（方便解析）：
```
只返回编号，用英文逗号分隔，不要写任何别的字。例如：3,1,7
如果都不符合，就只回复：无
```
解析时用正则只抠数字，容错 AI 多说几个字（比如"答案：3,1,7"）。

#### 5.1.6 ★ 分批搜索：已比对过的不再重复（用户 2026-10 要求）

**用户原话**：
> ai 同时对比的图片数量可以自定义，比如在三个分类条件筛选后的图有 100 张，
> 我自定义这次搜索其中的 30 张，在筛选条件和搜索框内容不变的情况下，
> 再次搜索，不会搜已搜过的图，并且再次搜索也可以自定义数量。

**实现**（`PhotoViewModel`）：

```kotlin
// 已经发给 AI 比对过的照片编号 —— 这是"不重复"的关键
private val aiSearchedIds = mutableSetOf<Long>
```

**每次搜索的流程**：
1. 按条件筛出**全部**候选
2. **跳过 `aiSearchedIds` 里的**，取接下来 `maxCandidates` 张
3. 比对完把这一批**记进** `aiSearchedIds`
4. 结果**累加**（之前批次找到的不会消失）

**"已比对记录"什么时候清空**（这三条很重要，不然会搜重或搜漏）：
| 触发 | 为什么 |
|---|---|
| **改了描述** | 换了搜索目标，之前的记录没意义 |
| **改了筛选条件** | 候选集合变了，旧记录的"第几批"对不上了 |
| **点「重新开始」** | 用户主动要求重头搜 |

**界面上显示**：`共 100 张符合条件　已比对 30 张　还剩 70 张`
按钮会变成 **「继续搜下一批（还剩 70 张）」**。

#### 5.1.7 ★ AI 先理解描述，必要时联网查资料（用户 2026-10 要求）

**用户原话**：
> ai 模型首先要理解用户输入的搜索内容，必要时可联网，
> 比如描述一张图的内容（一个人、一辆车这种大范围的内容），
> 同时如果用户输入的内容是某个动漫角色的名字，或者只输入某个作品名，
> ai 也要知道搜索这个作品中的角色。

**分两种情况处理**（这是关键设计）：

| 用户输入 | 要不要联网 | 为什么 |
|---|---|---|
| 「一个人」「一辆车」「一只猫」 | **不联网** | 大模型自己就懂，联网纯属浪费 |
| 「原神里的雷电将军」 | **联网查** | 模型可能不认识，需要查"她长什么样" |

**三步流程**：

```
① 理解：让 AI 输出 JSON {"search_query":"...", "plan":"..."}
 —— search_query 为空 = 不需要联网
② 联网：如果 search_query 非空，调 DeepSeek 搜索接口
③ 比对：把「用户描述 + 查到的资料 + 候选图」一起发给 AI
```

**联网搜索 API**（[官方文档](https://api-docs.deepseek.com/zh-cn/guides/search/)）：

| 项目 | 值 |
|---|---|
| 地址 | `POST {baseUrl}/v1/tools/search` |
| 参数 | `query`（1~128 字）、`count`、`need_content` |
| 计费 | **每 1000 次成功请求 5 元**（= ¥0.005/次） |
| **免费情况** | **搜索无结果不计费、失败不计费** ← 所以"不需要联网"时省钱 |
| 限速 | 每秒 5 次 |

**界面上给了开关**：☑「让 AI 先理解描述（可联网查资料）」
—— 关掉就更快更省，但认不出专有名词。

**花销变化**：
```
单张图 ¥0.001 + 理解/比对两次文字请求约 ¥0.001 + 联网搜索 ¥0.005
```
所以一次搜索（20 张）从约 ¥0.02 变成约 **¥0.026**（联网时多 ¥0.005，很便宜）。

> ⚠️ **联网搜索只在"需要"时才调用** —— 因为 `search_query` 为空就跳过，
> 所以搜"猫""车"这种日常描述**不会**产生这个费用。

#### 5.1.8 🚨 严重问题：搜索一张都返回不了（已修）

**用户实测**：
> 我指定的搜索范围内有很多张这个角色的图片，但我搜这个角色，**整个相册没有一张图返回**。
> 并且我看我的 API 调用只有 3 次，只消耗了不到 0.01 金额，
> 我感觉根本没有调用 AI 进行搜索。
> 我把这个相册中的这个角色的图片发给 DS 手机客户端问她这是什么角色，她都能回答正确的答案。

**用户给的诊断方向是对的**，而且他自己提出了正确的做法。

##### 根因：**任务设计错了 —— 把"比对题"出成了"识别题"**

原来的提示词是：
> 下面有 20 张候选图……请你挑出**最符合上面描述的**……
> 如果**都不符合**，就只回复：无

**"这张图是不是【某个动漫角色】"是一道识别题。**
如果模型不认识这个角色（或者只认识名字、不确定长相），
它**唯一安全的回答就是"无"** —— 于是 20 张全被排除，**一张都不返回**。

这也解释了"只调用了 3 次 API、花了不到 0.01 元"——
请求发出去了、也收到了回复，**但回复是"无"**。

> 而用户把图直接发给 DeepSeek 手机客户端时能答对，是因为那是**单图识别题**
> （只有一张图，模型只需要"认"），而我们是**20 张里挑**（模型需要"比对"）。
> **两种任务难度完全不同。**

##### ✅ 用户提出的正确做法（已按此实现）

> ai 搜索的逻辑应该是：
> **先理解用户给出的搜索内容，然后概括这个搜索内容的特征**，
> 如果是作品中的角色（如果 ai 不认识这个角色），就**联网搜索之后概括角色特征**，
> **再在待对比图库中一一比对**。

**新流程**：
```
① 理解 → 让 AI 输出一份**外形特征清单**（发色发型、服装样式颜色、配饰、体型…）
 + 判断要不要联网（不认识就搜）
② 联网 → 非空才搜，把资料也并进特征
③ 比对 → 提示词里放**特征清单**，问"哪张最符合这些特征"（比对题！）
```

**关键改动**：提示词从
> ❌「这张图**是不是**雷电将军？」
改成
> ✅「这几张里**哪张最符合**【紫色长发、和服、头饰、紫色眼睛】？」

模型**不需要认识这个角色**，只要照着清单在图里找特征就行。

**配套的"宽松"要求**（也是必须的，不然还是容易空手而归）：
- 角度不同、光线不同、清晰度低、侧脸背影、真人翻拍/cosplay、截图同人图 → **都不影响入选**
- 宁可选得多，不要漏
- 哪怕只有一半特征对上也要列出来（排后面）
- **只有明显完全不相干才排除**

##### 另外：加了"看 AI 的原始回复"诊断入口

"一张都没搜出来"时，光看一句"没有符合的"**根本查不出原因** ——
可能是不认识、可能是没听懂提示词、可能是返回格式没解析对。

所以现在把 **AI 的原始回复**（理解阶段 + 比对阶段）留着，
界面上有「**看 AI 的原始回复（排查用）**」按钮，点开就能看到。

> **教训**：**给大模型安排任务时，要选它擅长的题型。**
> "识别一个它可能不认识的专有名词"是它的弱项（它会保守地否认）；
> "按一份看得见的特征清单去比对"是它的强项。
> **同一个需求，换一种问法，结果天差地别。**
>
> 另外：**"花了钱但没结果"这种反馈极难排查**，
> 所以**一定要把模型的原始输出留下来给用户看**。这次就是因为看不到原文，
> 只能靠用户"只调用了 3 次、花了不到 0.01 元"这个旁证来反推。

#### 5.1.9 🚨🚨 真正的元凶：DeepSeek 的「思考模式」默认是开的

**上一节（5.1.8）我改了任务设计，但用户实测**：
> 回复是**空白的**

（界面上"AI 的原始回复"弹窗里，理解阶段和比对阶段**都是空白**。）

**这个"空白"就是决定性线索** —— 钱花了、请求成功了、但**一个字都没返回**。

##### 根因

查了 [DeepSeek 思考模式文档](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode/)：

> 思考模式**默认打开**，且 effort 默认为 `high`
> 在思考模式下，**思维链内容通过 `reasoning_content` 参数返回**，与 `content` 同级

**两件事同时踩了**：

| 问题 | 后果 |
|---|---|
| **我从没关过思考模式** | 模型把内容写进 `reasoning_content` |
| **我的代码只读 `content`** | 拿到**空字符串** |
| **`max_tokens` 还被思考吃光**（看图那步只给 200） | `content` 连"答案"都没有，`finish_reason` 是 `length` |

所以整个链路是"**成功但空白**"——
`response.isSuccessful == true`、不报错、钱照扣，**但拿到的正文是空的**。

##### ✅ 修法（三处）

**① 显式关掉思考模式**（三个请求都加）：
```kotlin
put("thinking", JSONObject.put("type", "disabled"))
```
理由：
- 看图比对要的是"一串编号"，**不需要长篇思考**
- 关掉后 token 全用在回答上，**又省又快**
- 而且**回答一定会出现在 `content` 里**，不会跑到 `reasoning_content`

**② 读不到 `content` 就回退读 `reasoning_content`**：
```kotlin
val content = message.optString("content").trim
if (content.isNotEmpty) return content
message.optString("reasoning_content").trim.ifEmpty { null } // ← 兜底
```

**③ `max_tokens` 调大**：理解阶段 800 → **4000**，看图比对 200 → **2000**。
（思考模式虽然关了，但留足余量总没错。）

**④ 诊断信息升级**：现在会把
**正文、思维链、解析出的编号、原始返回片段**全都列出来。
并且专门处理"正文和思维链都空"这种情况，直接提示"可能是 max_tokens 被思考吃光了"。

> ## 📌 这是这个项目最值得记的一课
>
> **"请求成功"不等于"拿到了内容"。**
>
> 失败的样子不只有"报错"这一种。这次是：
> **HTTP 200 + 不抛异常 + 扣了钱 + 正文是空字符串**。
> 如果不把**原始回复**留给用户看，这种 bug **几乎不可能查出来** ——
> 只能靠"花了钱但没结果"这种间接线索去猜。
>
> **两条通用做法**：
> 1. **调用大模型时，永远把原始回复（含 `reasoning_content`）留着并给用户看得到。**
> 2. **用"思考型"模型做"要求它输出固定格式"的任务时，先确认思考模式的状态** ——
> 开着会让 token 花在思考上，`content` 可能被挤空。
> 关掉它（`thinking: {type: "disabled"}`）通常**又快又省又稳**。

#### 5.1.10 AI 搜索结果单独开一页展示（用户 2026-10 要求）

**用户反馈**：

> 但我不清楚被排除的图片中有没有我想要搜索的角色，
> 所以做一个查看排除的图片的按钮。

**为什么这条要求很关键**：
复核用的是"**拿不准就算不是**"的**严格**策略 ——
好处是准确度高，**坏处是可能把对的也杀掉了**。

**用户反馈 3：数量显示 bug**
> 我先选择搜索数量，选择全部（如 300 张），修改筛选条件后待搜索的全部图片只有 200 张，
> 但按钮上显示的还是本次 300 张。

界面直接显示了前者。

**修法**：加一个派生值 `aiEffectiveBatch`，界面一律用它：
```kotlin
val aiEffectiveBatch = combine(
 settings.map { it.maxCandidates },
 _aiRemainingCount,
) { maxCandidates, remaining ->
 remaining.coerceAtMost(maxCandidates).coerceAtLeast(0)
}
```
这样显示的数字**永远不会超过实际存在的图**。

> **教训**：**"用户设定的值"和"实际能用的值"不是一回事，界面要显示后者。**
> 这类 bug 的共同特征是"**显示的数字比现实还大**"——
> 用户一看就觉得不对，但代码里每处都"没错"（只是显示错了对象）。

#### 🐛 滚轮"回到初始位置时不生效"—— `LaunchedEffect` 捕获旧值（用户 2026-10 反馈）

**用户原话**：
> 不行，左侧滑倒顶端之后，当前范围还是卡着不变，右侧可选年份也没变。

**前面那次没修对。** 真正的根因是 **`LaunchedEffect` 的键里没有 `selectedIndex`**：

```kotlin
LaunchedEffect(listState, lastIndex) { // ← 键不含 selectedIndex
 snapshotFlow { listState.isScrollInProgress }.collect { scrolling ->
 if (!scrolling) {
 val i = computeCenter
 if (i != safeIndex) onSelected(i) // ← safeIndex 是**首次组合**捕获的旧值
 }
 }
}
```

`lastIndex` 不变 → 这个 effect **只启动一次** → 里面的 `safeIndex` **永远是初始值**。

于是出现了极其刁钻的症状：

| 操作 | computeCenter | 与旧 safeIndex(0) 比较 | 结果 |
|---|---|---|---|
| 往下滚到第 5 项 | 5 | 5 ≠ 0 | ✅ 上报 5 |
| 再滚回最顶（第 0 项） | 0 | **0 == 0**（旧的 0） | ❌ **判定"没变"，不上报** |

**"回到初始位置时永远不生效"** —— 正是"滑到顶端范围卡住不变"的真凶。
所以看起来"大部分位置都正常，只有回到起点不行"。

**修法**：
```kotlin
val safeIndexNow by rememberUpdatedState(safeIndex)
...
if (i != safeIndexNow) onSelected(i)
```

> **教训（很重要，通用）**：
> **`LaunchedEffect` / `remember` 的 lambda 捕获的是"那一刻"的值，不是最新值。**
> 只要 effect 的**键不变**，它就不会重启，里面读到的所有外部变量**都是陈旧的**。
>
> 判断方法：**"effect 里的逻辑会不会在首次组合之后还需要读新值？"**
> 会 → 那个值必须用 `rememberUpdatedState` 包一层。
>
> 这个 bug 之所以难查，是因为它**只在"值恰好回到初始值"时暴露** ——
> 其它位置全都正常，看起来完全不像"状态没更新"的问题。

#### ✅ 年份全选时按"不限"处理（用户 2026-10 要求）

**用户原话**：
> 在起始年份选择最老，结束年份选择最新时，缩略图界面的年份按钮应该显示不限，
> 而不是把具体年份显示出来。

**做法**：在「确定」时判断，如果选中的就是**全部年份**（最老 + 最新），
直接存 `null`（= 不限），而不是存一个和"不限"完全等价的范围。

```kotlin
s == asc.first && endYear.value == asc.last -> onPick(null)
```

对话框里的"当前范围"也相应显示「**不限（全部年份）**」，
让用户知道这个选择等于没筛。

> **教训**：**界面上"看起来一样"的两个状态，不该存成不同的值。**
> "筛选全部"和"不筛选"在结果上完全等价，
> 存成同一个状态（null）可以让显示、计数、缓存键全部天然一致，
> 免得后面每一处都要写"如果等于全集就当作没筛"。

#### 🐛 `user_text` 必须是**三态**，不能只有"空/非空"（用户 2026-10 反馈）

**用户原话**：
> 有些没有文字的图片，机器扫描出来会有文字，我需要把识别出来的文字删掉，
> 但是删完又变成机器识别的文字了。

**根因**：我一开始把 `user_text` 设计成"空 = 没动过，回退用机器文字"。
于是**用户永远删不掉**机器认错的文字 —— 删空 → 存空 → 读出来又回退到机器文字。

**✅ 改成三态**：

| `user_text` | 含义 | 生效的文字 |
|---|---|---|
| `null` | **没动过** | 机器识别的 `ocr_text` |
| `""`（空串） | **用户明确删空了** → 这张图就是没字 | **空**（不回退） |
| 有内容 | 用户补/改过 | 用户写的 |

```kotlin
val effectiveText: String
 get = if (userText != null) userText else ocrText.orEmpty
```

**配套改动**：
- `saveUserText` **不再把空串转成 null**（这是 bug 的根源）
- 新增 `restoreMachineText` → 把 `user_text` 设回 `null`
- 编辑弹窗里新增「**恢复机器识别结果**」按钮（**只有改过之后才出现**）
- 输入框为空且原来有机器文字时，提示"保存后这张图就当作没文字"，
 免得用户以为是"恢复机器文字"

> **教训**：**"空值"和"没填"是两回事，数据库字段一定要能区分。**
> 用 `null` 表示"没动过"，用 `""` 表示"明确清空"，
> 这个区分在"允许用户覆盖系统默认值"的场景里**必须有**，
> 否则用户就**没有手段表达"我就是要空"**。

#### 🐛 年份滚轮快速滑动时"抖"（用户 2026-10 反馈）

**用户原话**：
> 在滚轮选择年份的时候，快速滑动会导致年份文字出现跳动鬼畜。

**根因：双向绑定形成了回环**

```
居中项变化 → onSelected 通知父级 → 父级改 selectedIndex
 → LaunchedEffect 又 scrollToItem(selectedIndex)
 → 和正在进行的惯性滑动抢位置 → 抖
```

快速滑动时"居中项"**每帧都在变**，这个回环每秒触发几十次，
两个方向的滚动指令互相打架，画面就跳。

**✅ 现在的做法（三条）**：

1. **只在滚动停下来之后**才通知父级（不再每帧通知）
 ```kotlin
 snapshotFlow { listState.isScrollInProgress }
 .collect { scrolling -> if (!scrolling) onSelected(centeredIndex) }
 ```
2. **高亮跟着实时位置走**（用 `derivedStateOf`），视觉上依然跟手
3. **只有列表长度变化时**才主动滚一下（把越界位置拉回来），
 平时绝不主动滚动

**另外顺带修了"居中项算错"的隐患**：
原来是 `minByOrNull { abs(it.offset) }` —— 那是**离视口顶边最近**的项，
不是中间那项。现在按**视口中线**算：

```kotlin
val center = (info.viewportStartOffset + info.viewportEndOffset) / 2
items.minByOrNull { abs(it.offset + it.size / 2 - center) }
```

> **教训**：**"UI 控件 ↔ 外部状态"双向同步时，必须有一方是"只读的权威源"。**
> 滚轮的位置应该由**滚动本身**决定，外部状态只做初始值和越界修正；
> 一旦外部状态反过来每帧驱动滚动，就会和惯性动画打架。
>
> 还有一个通用判断：**"每帧都可能变化的量"绝对不能无条件触发"会改变滚动位置的操作"**。

#### 3.5.5 🐛 换相册时要**立刻中止**识别（用户 2026-10 反馈）

**用户原话**：
> 在文字识别过程中切换相册，识别应该自动取消，而不是继续。

**症状**：识别跑着的时候去扫别的相册，识别**照旧继续跑**，
进度条一直走，但那些照片记录马上就被删掉了 —— 纯属白跑。

##### 根因：取消的时机放错了地方

我一开始的想法是"监听到相册变了就取消"。
但**相册名是扫描结束后才变的**（要等新照片写进数据库）——
等它变才取消，整个扫描期间识别都还在跑，**根本来不及**。

##### ✅ 修法：取消放在**扫描开始时**

```kotlin
private fun scanAlbumInternal(album: AlbumInfo) {
 abortOcrQuietly // ← 先中止识别
 viewModelScope.launch { repository.scanAlbum(album) { ... } }
}
```

##### ⚠️ 为什么不能用现成的 `cancelOcr`

`cancelOcr` 是"用户主动点取消"的语义，它收尾时会把**剩下的照片标记成"跳过"**。
直接拿来用会出问题：

| 情况 | 后果 |
|---|---|
| 给即将被删掉的旧照片标"跳过" | 没意义（马上就被删了） |
| **万一标记晚于新相册写入** | **把新相册的照片全标成"跳过"** → 界面莫名显示"还有 N 张未识别（上次取消了）" |

所以新增了一条独立路径 `abortOcrQuietly`：
- **只叫停**（`repository.abortOcrQuietly` 置标志 + `ocrJob.cancel` 强停）
- **不标记跳过**
- 进度归零

对应仓库里多了一个 `ocrAbortQuietly` 标志，循环收尾时按它决定标不标：

```kotlin
val quiet = ocrAbortQuietly
if (!quiet) dao.markRemainingSkipped // 只有用户主动取消才标
```

> **教训**：**"同一个动作"在不同场景下收尾方式可能完全不同。**
> "用户点取消"要留着痕迹（标记跳过，下次能接着来）；
> "因为客观原因被打断"（换相册）就该**干净地消失**，不留任何痕迹。
> 把两者塞进同一个函数，迟早会在角落里炸出来。

#### 5.1.12 ★ 理解阶段只做一次，跨批次复用（用户 2026-10 要求）

**用户原话**：
> ai 搜索过一次后，继续搜索剩下的图时，ai 搜索的理解阶段应该不变，
> 不要搜索一次就重新理解一遍，这样会导致理解误差让搜索不准确。

**这个判断完全正确，原因很具体**：

理解阶段是把「无声铃鹿」翻译成一份特征清单。**每次调用模型，措辞都会略有不同**：

| 第一次 | 第二次 |
|---|---|
| 浅**栗**色中长发、马耳、紫红眼睛 | 浅**棕**色中长发、马耳、紫红色眼睛 |

**判断标准就飘了** —— 第一批按"浅栗色"挑、第二批按"浅棕色"挑，
用户会觉得"同样的搜索怎么时好时坏"。

**而且白花钱**：理解阶段包含一次联网搜索（¥0.005/次），每批都重做就是重复付费。

##### 实现

1. `Understanding` 从 `private` 改为**公开**，并加 `forDescription` 字段
 （记住"这份理解是基于哪条描述算的"）
2. `search` 新增 `cachedUnderstanding` 参数，**有缓存就直接用、不再调接口**
3. `Result` 带回 `understanding`，ViewModel 存进 `aiUnderstanding` 字段
4. ViewModel 下一批把 `aiUnderstanding` 传进去

**缓存怎么保证不会用错**：
```kotlin
val reusable = cachedUnderstanding?.takeIf {
 useUnderstanding && // 用户没关掉理解开关
 it.forDescription == description && // 描述没变
 it.features.isNotBlank // 上次确实算成功了
}
```
三个条件都满足才复用，否则重新理解。所以**改了描述会自动重算**，不用手动清。

**什么时候清缓存**：
| 情况 | 清吗 | 为什么 |
|---|---|---|
| 换相册 | **清** | 换了一整个照片库 |
| 改描述 | 自动失效 | `forDescription` 不匹配 |
| 改筛选条件 | **不清** | 条件不影响"这东西长什么样"，标准该一致 |
| 点「重新开始」 | **不清** | 按钮写的是"忘掉已比对记录"，没说要重新理解 |

**界面提示**：复用时会显示「**沿用上次的理解结果，正在比对…**」，
让用户知道这次没有重复理解。

> **教训**：**调大模型时，"同一件事"要固定下来，不要反复问。**
> 模型对同一个问题会给出措辞不同的答案 ——
> **凡是"结论要给后续步骤当基准"的调用，都应该缓存起来复用**，
> 否则每一步的基准都在微小漂移，最后结果就不可复现了。
